{% if tab == "method" %}
  1. 1Load the file

    One CSV per period, loaded straight into a table with every column as text. The periods present in the drop are the periods that get loaded; some games are missing part of the third and the whole of overtime.

  2. 2Unpack the image id

    Image Id packs the game, the teams and the frame into one string: 2025-11-28 Team J @ Team K_065468. The first 26 characters are the game id, and the last six are the frame number.

  3. 3Turn the clock into a running total

    The clock counts down and restarts every period, so it is replaced with time_elapsed: seconds since the opening faceoff. About one row in a thousand has no clock at all and is dropped, and the count is kept.

  4. 4Face the rink one way

    Teams change ends between periods, so a position from period 1 and the same position from period 2 are mirrored. The camera table says which team had its goalie on the right in the first period, and the periods that leave the home end the wrong way are rotated 180 degrees - both axes, so a player keeps their own side of the ice.

  5. 5Put the puck in every row

    The puck is a row like any other. Its position is joined onto every player in the same frame, which is what makes distance to the puck possible.

  6. 6Find who is holding it

    The player nearest the puck is ranked first, and must also be within six feet of it to be given possession. Six feet is about a stick length: nearer and the puck is at their feet, further and it is loose.

  7. 7Name the defenders

    On frames where the other team has the puck, a defender is Primary if they are the nearest defender or within six feet of the puck, and Secondary otherwise.

  8. 8Attach the state of the game

    Neither file carries strength or score in the tracking data, so both come from the event file, turned into windows with a start and an end. A game returns to states it has already been in, so the windows are numbered spells rather than groups by state.

  9. 9Add the lines and the zones

    Every position is dropped into one of the 58 zones from HockeyRinkZones.geojson, for the player and for the puck separately, and the duplicate rows left by the joins are reduced to one per player per frame.

Two things to be careful with

Overtime coordinates follow a different rule

In regulation the event file uses the same absolute rink frame as the tracking: x is a place on the ice, and it flips when the teams change ends. In overtime it does not. Both teams' coordinates are attack-normalised, so x points at the goal the eventing team is attacking, whoever that is.

That is measurable rather than guesswork. Comparing every overtime event against the tracked puck at the same second, the home team's event x correlates -0.94 with the tracking and the away team's +0.90, and the same holds for y. A mirrored team is a rotated team.

Two consequences. Overtime events cannot be plotted with regulation events without undoing the rotation first, and the assumption of which team gets rotated is only tested on the three overtime games in this drop, all of which are camera-Away games. A camera-Home overtime game would settle it and there is not one here.

Positions and sides are estimated, not recorded

There is no position column in the release. Forward, defence and centre are inferred from where players stand at neutral zone faceoffs: the players nearest their own blue line are the forwards, the two nearest their own goal line are the defence, and the player on the dot is the centre. The same standing positions give the side.

Ten games is not enough to be certain about any single player. A player who took thirty neutral zone faceoffs is well evidenced; one who took four is not, and a player who rarely starts a faceoff at all is guessed at from a handful of frames. Take the position and the side with a grain of salt - more games would make the estimate worth trusting, and this drop does not have them.

Things worth knowing before trusting a number

WhatWhy it matters
player_id is a track, not a person The tracker re-issues ids when it loses and re-acquires a player: {{ "{:,}".format(meta.track_ids) }} ids for {{ meta.players }} players in one game, 132 of them on the goalie alone. Anything per player groups on (team, jersey).
Goalies are marked Go The jersey column holds Go instead of a number for goalies, and blanks for players whose number was not read. It is the only goalie marker in the data.
Blank and n/a are different things Puck rows carry n/a in the team and id columns and blanks in the coordinates. Both mean not applicable, and both have to become NULL before the columns can be typed.
Not every player is in every frame About eight players per frame instead of ten skaters and a goalie, so a count is "seen here", not "was here".
Some periods are missing Part of the third period is absent in several games and period 3 is often a fifth of a game. Anything summed across a game inherits that hole.
Overtime ends The tracking mirror treats overtime like period 2, and the tracked puck confirms it for the three overtime games here.

MySQL is the workshop and Supabase is the serving copy. Everything is built locally, checked against the raw files, and then loaded: the site never writes to the database, it only reads.

How the copy works

The loader does not implement the copy itself. It calls scripts/reload_supabase_table_from_mysql.py in the parent repo, the same script every other table in this project uses, so there is one implementation of that logic rather than two. That script reads MySQL with a cursor and streams the rows into Postgres with COPY, writing values with write_row rather than formatting CSV, and it runs with prepare_threshold=None so the pgbouncer pooler is happy.

Three things follow from the pooler and the instance size, and each of them cost a failed load to find:

  • Use the session pooler, not the transaction pooler. The same host serves port 6543 for transaction pooling and 5432 for sessions. A COPY holds its connection for the whole transaction, and transaction mode answers that with a checkout timeout after fifteen seconds. The loader rewrites the port.
  • Free space before loading. Over its storage limit Supabase writes default_transaction_read_only = on into postgresql.auto.conf, and every write then fails with ReadOnlySqlTransaction partway through a load.
  • Vacuum after the indexes. Building an index does not set the visibility map, and an index-only scan without it still fetches from the heap. On this data that was 170,000 heap fetches per query until a VACUUM ran.

What is derived in Supabase

Three tables are built there rather than shipped from MySQL, because they are views of the tracking data for the pages rather than sources of truth:

  • bdc2026_frames - one row per frame, 959,007 of them, carrying what is true of the frame: the puck's zone and position, the states, who had possession. Built by build_frames.py.
  • bdc2026_game_players - which jerseys appear in which game, 410 rows, so a game can narrow the player menu without scanning the tracking table.
  • bdc2026_rink_zones - the 58 rink polygons, loaded by add_boxids.py with PostGIS, which is what resolves boxid and boxid_puck.

Derived means rebuildable: build_frames.py truncates and refills, and nothing else depends on it.
